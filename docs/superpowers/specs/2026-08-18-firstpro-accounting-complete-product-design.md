# FirstProAccounting — المواصفة التنفيذية الشاملة

**التاريخ:** 2026-08-18

**الحالة:** مواصفة تنفيذية مبنية على التصميم المعتمد من المستخدم، وتحتاج مراجعة نهائية قبل بدء دفعات التوسع التالية.

**المالك:** Manus AI

## 1. الهدف

تحويل FirstProAccounting إلى تطبيق Android محاسبي وتشغيلي عملي للمحلات الصغيرة والمتوسطة، بحيث يخدم التجارة العامة، الخدمات، صيانة الهواتف والأجهزة، المخابز والمعاجن، مع الحفاظ على صحة القيد المزدوج، دقة المخزون والتكلفة، سلامة العملات والضرائب، قابلية التدقيق، وسهولة الاستخدام على الهاتف.

تُنفّذ التوسعة فوق النواة الحالية دون إعادة كتابة تاريخية أو حذف ميزات. كل سلوك مالي جديد يجب أن يكون قابلاً للاختبار، ويجب أن يمر عبر معاملة قاعدة بيانات واحدة عندما تكون العملية مركبة، مع بوابة تحقق GitHub Actions قبل الانتقال إلى الوحدة التالية.

## 2. حدود النطاق

يشمل النطاق إكمال وحدة الخدمات والصيانة، ربطها بواجهة Flutter والتنقل والصلاحيات، تعميق اختبارات المالية والخدمات، بناء وحدة إنتاج للمخابز والمعاجن، تدقيق المخزون والوحدات التجارية والتسويات، مراجعة الضرائب والعملات والفترات والإلغاءات، استكمال التقارير ودفتر الأستاذ والتدقيق، ثم اختبارات الترحيل والقبول وتحسين الجاهزية النهائية لـ Android.

لا يشمل النطاق إعادة كتابة المشروع من الصفر، تغيير قاعدة البيانات مباشرة دون Migration، حذف بيانات المستخدم التاريخية، أو إضافة خدمات سحابية إلزامية لا يحتاجها التطبيق المحلي. لا تُضاف المواعيد أو التصنيع المتقدم أو نظام ERP واسع ما لم يثبت أنه ضروري لسلوك محاسبي محدد.

## 3. القيود الثابتة

| القيد | القرار الملزم |
|---|---|
| الفرع | العمل على `main` مباشرة، دون إنشاء worktree. |
| Flutter المحلي | لا تثبيت حزم Flutter محلياً للفحص فقط؛ التحقق النهائي عبر GitHub Actions. |
| قاعدة البيانات | SQLite/SQLCipher الحالية، وكل تغيير Schema عبر Migration جديد فقط. |
| الإصدارات التاريخية | عدم تعديل migrations من v2 إلى v56 وعدم فقدان البيانات التاريخية. |
| الدقة المالية | تخزين القيم المالية كوحدات صغرى صحيحة، واستخدام محركات النواة الحالية للتحويل والضريبة والإجماليات. |
| القيود | كل قيد متوازن، قابل للتدقيق، مرتبط بالعملة والفترة والمرجع، ولا يحذف بعد الترحيل. |
| المخزون | لا حركة عند المسودة؛ الحركة فقط عند الترحيل أو التسوية المعتمدة وبسياسة الصنف. |
| الاختبارات | TDD لكل سلوك جديد، ثم اختبارات الوحدة والتكامل والقبول والانحدار. |
| CI | لا تعتبر المرحلة مكتملة قبل نجاح `flutter analyze` و`flutter test` وبناء APK وAAB. |
| UI | Material 3، خط Cairo، دعم العربية والإنجليزية وRTL/LTR، وعدم كسر النمط الحالي. |

## 4. المعمارية المستهدفة

تبقى طبقة الواجهة معتمدة على Provider وChangeNotifier، وتبقى الخدمات التشغيلية في `lib/data/datasources/services/`، والنماذج في `lib/data/models/`، والسياسات والمحركات النقية في `lib/core/`. تُستخدم GetIt لتسجيل الخدمات، وتُمرر عمليات قاعدة البيانات المركبة عبر المعاملة نفسها بدلاً من تحديثات منفصلة قد تترك أرصدة جزئية.

تكون النواة المالية مصدر الحقيقة الوحيد للحسابات؛ فلا تعيد الواجهات أو ViewModels حساب الضريبة أو تحويل العملة أو إجماليات المستندات بطريقة مستقلة. وتكون سياسات ProductKind، وحالة المستند، والفترة المالية، والصلاحيات حواجز قبل الترحيل وليس بعده.

تُقسّم التوسعة إلى وحدات مستقلة ذات مخرجات قابلة للتحقق:

| الوحدة | المخرج القابل للتحقق |
|---|---|
| الخدمات والصيانة | دورة أمر خدمة كاملة، دفعات، ضمانات، واجهة، ترحيل وإلغاء. |
| الاختبارات المالية | سيناريوهات عكسية ومتعددة العملات والضرائب والمخزون دون تذبذب. |
| الإنتاج | وصفة، أمر إنتاج، استهلاك خامات، إنتاج تام، هالك، تكلفة وقيد متوازن. |
| المخزون التجاري | وحدات، تحويلات، جرد، تسويات، مرتجعات، وحواجز السالب. |
| الضرائب والعملات | تطبيق مركزي ودقيق على المستندات والدفعات والتقارير. |
| التقارير والتدقيق | دفتر أستاذ وميزان مراجعة وتقارير تشغيلية تعكس القيود الفعلية. |
| Android والتشغيل | أداء، صلاحيات، نسخ احتياطي، ترحيل، وتجربة استخدام قابلة للتسليم. |

## 5. القواعد المحاسبية غير القابلة للتفاوض

يجب أن تنتج كل عملية مالية قيداً مزدوجاً متوازناً أو لا تنتج أي أثر. لا يُسمح بتعديل رصيد حساب أو كمية مخزون مباشرة خارج الخدمة المسؤولة عن القيد أو الحركة. لا يُسمح بإلغاء القيد الأصلي أو حذفه؛ الإلغاء يتم بقيد عكسي مستقل مع مرجع وسبب ومستخدم وتاريخ.

تُحسب مبالغ العملة الأصلية بالوحدات الصغرى، ويُحتفظ بالعملة ومعدل الصرف والمبلغ الأساسي المحسوب بمحرك مركزي. تستعمل حركات COGS والمخزون العملة الأساسية فقط عندما يفرض نموذج التكلفة ذلك، ويُمنع استدعاء خدمات قد تفتح استعلاماً جديداً من داخل معاملة SQLite إذا كان ذلك يسبب deadlock.

الخدمة غير المخزنية لا تؤثر في `products.current_stock` ولا في COGS. قطعة الغيار المخزنية لا تؤثر في المخزون عند إنشاء المسودة، بل عند الترحيل المعتمد فقط. المنتجات غير المخزنية والحزم تتبع ProductKind والسياسة المركزية، ولا يجوز تجاوز السياسة من الواجهة.

## 6. المراحل التنفيذية

### المرحلة A: إكمال الخدمات والصيانة

يُستكمل التحقق من الدفعات بمنع الصفر والسالب والتجاوز والتكرار، مع تحديث المتبقي من رأس الأمر وإيداع القيد عبر JournalService دون تعديل رصيد مباشر. تُستكمل الضمانات بقيود زمنية واضحة، دون إنشاء قيد عند إنشاء الضمان.

بعد ذلك تُبنى شاشة القائمة والتفاصيل والتحرير والتسليم والتحصيل، وتُربط route وdrawer أو navigation وفق نمط الشاشات الحالية. تُعرض الحالات المسموحة، وتُمنع العمليات المحاسبية الخطرة برسائل واضحة، وتُحترم الصلاحيات وسجل التدقيق.

**بوابة النجاح:** اختبارات الدفعات والضمانات، اختبار قبول UI/flow، عدم وجود حركة للخدمة، وجود حركة وCOGS للقطعة، نجاح CI والبناء.

### المرحلة B: الاختبارات المالية العميقة

تُضاف اختبارات property-like وregression للقيود المتوازنة، الدقة بالوحدات الصغرى، تحويلات العملات، الخصومات والضريبة والنقل، الإلغاء، الفترات المغلقة، الترحيل المكرر، وتعارضات المخزون. تُراجع الاختبارات الحالية وتُضاف حواجز مصدرية لكل إدراج مالي جديد حتى لا تُفقد metadata.

**بوابة النجاح:** عدم وجود مسار مالي غير مختبر في الوحدات المتأثرة، نجاح الاختبارات القديمة والجديدة، ونجاح CI.

### المرحلة C: الإنتاج والتكلفة للمخابز والمعاجن

تُضاف نماذج الوصفات ومكوناتها وأوامر الإنتاج وسجل الإنتاج والهالك، مع Migrations جديدة وفهارس مناسبة. تحدد الوصفة كمية الخام اللازمة لوحدة إنتاج، وتُحسب التكلفة من محرك التكلفة الحالي أو محرك إنتاج جديد مع وحدات صغرى ثابتة.

عند اعتماد أمر الإنتاج، تُنقص الخامات بحركات استهلاك، وتزيد المنتجات التامة بحركات إنتاج، ويُرحّل فرق التكلفة وفق حسابات المخزون والإنتاج والهالك. لا تُنفذ العملية جزئياً، وتُمنع الوصفة الدائرية أو المكونات السالبة أو الإنتاج فوق صلاحية المخزون دون سياسة واضحة.

**بوابة النجاح:** اختبار وصفة، استهلاك خامات، إنتاج تام، هالك، تكلفة، منع الكمية غير الكافية، عكس أمر الإنتاج، وميزان قيد متوازن.

### المرحلة D: المخزون والوحدات التجارية

تُراجع أنواع المنتجات، الوحدات الأساسية والتحويلية، الحزم، الأصناف غير المخزنية، المستودعات، الجرد، التسويات، التحويل بين المستودعات، والمرتجعات. كل عملية تؤثر في الكمية يجب أن تسجل مرجعاً ومستخدماً وتاريخاً وسبباً، وأن تحدث الكمية عبر مسار مركزي.

تُطبق سياسة واضحة للسالب: يُمنع افتراضياً في الأصناف المتتبعة بالتكلفة، ويُسمح فقط إن كانت إعدادات النشاط والسياسة تبرر ذلك مع أثر تدقيقي صريح. لا تُخلط كميات المبيعات مع المخزون المحاسبي إذا فشل الترحيل.

**بوابة النجاح:** اختبارات الجرد والتسوية والتحويل والمرتجع والوحدة والحزمة والسالب، ثم CI.

### المرحلة E: الضرائب والعملات والفترات والإلغاءات

تُراجع جميع مسارات المبيعات والمشتريات والخدمات والدفعات والمصروفات للتحقق من استعمال TaxEngine وCurrencyEngine وInvoiceTotalsEngine. تُمنع الضريبة المزدوجة، وتُثبت طريقة التقريب، وتُراجع الحسابات المستحقة والضريبة المخرجة والمدخلة.

تُطبق حواجز الفترة المفتوحة على كل ترحيل مالي، وتُحدد سياسة الإلغاء في فترة لاحقة إذا كانت الفترة الأصلية مغلقة. تُراجع فروقات الصرف والتسويات، وتُحفظ المبالغ الأصلية والأساسية دون استخدام floating-point لإنتاج قيمة محاسبية.

**بوابة النجاح:** سيناريوهات عملة أجنبية، معدل صرف، ضريبة، فترة مغلقة، إلغاء في فترة لاحقة، وفروق صرف، مع التوازن والتدقيق.

### المرحلة F: التقارير والتدقيق والصلاحيات

تُراجع تقارير دفتر الأستاذ وميزان المراجعة والأرباح والخسائر والذمم والمخزون وCOGS والتدفقات التشغيلية، بحيث تعتمد على القيود والحركات الفعلية لا على حقول مشتقة غير مضمونة. تُربط أوامر الخدمة والإنتاج والإلغاءات بمراجع قابلة للبحث.

تُراجع صلاحيات الوصول للعمليات الحساسة مثل الترحيل والإلغاء والتسويات والإنتاج وتعديل الإعدادات، ويُسجل الفشل والنجاح والسبب والمستخدم. لا تُعرض الأسرار أو رموز فتح الأجهزة أو معلومات حساسة غير محمية.

**بوابة النجاح:** مقارنة التقارير مع قيود اختبار معروفة، اختبار منع الصلاحيات، اختبار سجل التدقيق، ونجاح CI.

### المرحلة G: الترحيل والقبول والجاهزية Android

تُضاف اختبارات ترحيل من قواعد قديمة حتى آخر إصدار، مع اختبار قاعدة فارغة وقاعدة تحتوي بيانات واقعية اصطناعية. تُنفذ اختبارات قبول تغطي نشاط التجارة والخدمات والصيانة والمخبز، ثم يُفحص الأداء، وعمليات النسخ الاحتياطي والاستعادة، وقفل التطبيق، والعمل دون شبكة إذا كان المسار الحالي يدعم ذلك.

تُراجع إعدادات Android، حجم الحزمة، الأذونات، عدم تسريب قاعدة البيانات أو مفاتيحها، وسلوك الترقية. يكون البناء النهائي عبر GitHub Actions، مع حفظ رقم commit ورقم تشغيل CI ونتيجة كل خطوة.

## 7. استراتيجية الاختبار

لكل ميزة جديدة يبدأ التنفيذ باختبار فاشل يثبت السلوك المطلوب. بعد ذلك يُكتب الحد الأدنى من الكود، ثم تُشغل اختبارات الوحدة، التكامل، قاعدة البيانات، Widget، والقبول بحسب نطاق التغيير. لا يُعد اختبار يمر قبل تنفيذ الميزة دليلاً على صحة السلوك.

| نوع الاختبار | نطاقه |
|---|---|
| Unit | محركات المال والضريبة والعملات والسياسات والنماذج. |
| Database/Migration | المخطط، الفهارس، القيم الافتراضية، وترقية قواعد الإصدارات السابقة. |
| Integration | الخدمات، الإنتاج، المخزون، القيود، الدفعات، والإلغاءات. |
| Acceptance | سيناريوهات التاجر ومحل الخدمة والمخبز من الواجهة أو طبقة التشغيل الكاملة. |
| Regression | منع عودة أخطاء deadlock، القيد غير المتوازن، الترحيل المكرر، وفقدان metadata. |
| Static/source guards | حظر الإدراجات المالية غير المكتملة والاستدعاءات غير الآمنة داخل المعاملات. |
| Android CI | analyze، test، APK، AAB، والتوقيع/الرفع وفق workflow الحالي. |

## 8. استراتيجية الفروع والالتزامات

يُحفظ كل تسليم منطقي في commit صغير قابل للمراجعة على `main`. لا يُدفع كود إنتاج جديد دون اختبار مرتبط به. بعد كل دفع تتم مراقبة تشغيل GitHub Actions، ويُحفظ سبب الفشل وإصلاحه في سجل العمل الخارجي. إذا فشل CI بسبب خطأ حقيقي، يُكتب اختبار انحدار عند الإمكان قبل إصلاح السبب وإعادة الدفع.

## 9. معايير الإكمال النهائي

يُعتبر المشروع جاهزاً لهذه الخطة فقط عندما تكون الوحدات المحددة في النطاق منفذة ومستخدمة من الواجهة أو خدمة تشغيل موثقة، وتكون العمليات المالية متوازنة، وحركات المخزون قابلة للتدقيق، والضرائب والعملات دقيقة، والتقارير متسقة، والصلاحيات والنسخ الاحتياطي مختبرة، ونجح Android CI الكامل دون فشل.

لا تُعتبر التحذيرات غير المانعة في أدوات GitHub Actions فشلاً وظيفياً، لكنها تُسجل كديون تقنية منفصلة ولا تُخفى عن المستخدم. أي بند لم يمكن إثباته بالاختبار يُصنف صراحة على أنه غير مثبت، ولا يُعلن اكتماله بالتخمين.

## 10. الملفات المتوقعة

ستُضاف أو تُعدل الملفات بحسب الحاجة الفعلية وبعد فحص الموجود، مع الحفاظ على حدود المسؤولية:

- `lib/data/datasources/migrations/migration_v*.dart` و`schema.dart` عند الحاجة إلى Schema جديد.
- `lib/data/models/` للنماذج التشغيلية.
- `lib/core/finance/` و`lib/core/service/` وطبقات السياسات لمحركات نقية قابلة للاختبار.
- `lib/data/datasources/services/` للخدمات المعاملية والتكامل مع JournalService وStockService وCostingEngineService.
- `lib/ui/screens/` و`lib/ui/navigation/` و`lib/ui/widgets/` لواجهات التشغيل.
- `test/core/`, `test/unit/`, `test/integration/`, `test/acceptance/`, `test/regression/` للاختبارات حسب الطبقة.
- `AGENTS.md`, `docs/`, وملف سجل العمل الخارجي للتوثيق.

## 11. قرارات مؤجلة لا تمنع البدء

يُستخدم الحساب الافتراضي الحالي عندما لا يحدد المنتج أو الوصفة حساباً متخصصاً، مع تسجيل ذلك في التوثيق. يُبنى الإنتاج بوصفة خطية في المرحلة الأولى، وتُرفض الدورات أو التراكيب المتقدمة بدلاً من قبول نتيجة تكلفة غير موثوقة. تُحافظ واجهة الخدمات على نمط التطبيق الحالي قبل أي إعادة تصميم مرئية واسعة.

أي قرار يتطلب تغييراً محاسبياً جوهرياً، مثل السماح بالسالب أو معالجة الإنتاج في فترة مغلقة، يجب أن يظهر في اختبار وسياسة صريحة قبل اعتماده.
