# تصميم تهيئة الدولة والنشاط وجاهزية الإنتاج

**الحالة:** مقترح للمراجعة والاعتماد قبل التنفيذ

**الإصدار الأول:** اليمن

**الإصدارات اللاحقة:** دول إضافية دون تغيير النتائج التاريخية للمستخدمين السابقين

## 1. القرار المعماري

يستخدم التطبيق نواة محاسبية واحدة لجميع الأنشطة، ولا ينشئ نسخة منفصلة للتجارة أو الخدمات أو المخابز. تُفصل أربعة مفاهيم يجب ألا تختلط: ملف النشاط، الدولة والنظام الضريبي، العملة وسعر الصرف، وواجهة العرض/الاختصارات.

اختيار نشاط التاجر يضبط الاختصارات والقوالب والمساعدة وترتيب الوحدات فقط. لا يغيّر نوع النشاط القيد المزدوج أو حسابات المخزون أو سياسة الإلغاء أو السجل التاريخي، ولا يحذف أي ميزة أو بيانات.

## 2. نموذج البيانات المقترح

يُضاف عبر Migration جديد نموذج typed أو جداول/واجهات مكافئة للآتي:

| الكيان | المسؤولية |
|---|---|
| `business_profile` | الاسم، العنوان، الهاتف، الرقم الضريبي، الدولة، النشاط/الأنشطة، حالة اكتمال الإعداد |
| `tax_regimes` | نظام الدولة، تاريخ السريان، طريقة الضريبة، قواعد الإدخال والإخراج، حقول الفاتورة |
| `tax_codes` | خاضع، معفى، صفري، معدل خاص، مع تاريخ السريان وحسابات الضريبة |
| `workspace_settings` | العملة الأساسية، السنة المالية، المستودع والصندوق الافتراضيان، وسياسة الإعداد |
| `presentation_preferences` | الوحدات المفعلة، ترتيب الاختصارات، إظهار/إخفاء العرض فقط، آخر خطوة في المعالج |
| `document_tax_snapshot` أو أعمدة المستند/البند | رمز الضريبة والمعدل والمبلغ والنظام وقت الترحيل |

لا تُستخدم جداول العملات لحفظ قواعد الدولة أو الضريبة. العملة تحفظ الكود والاسم والرمز والدقة وتاريخ أسعار الصرف فقط. الدولة والنظام الضريبي منفصلان.

## 3. قاعدة عدم تغيير التاريخ

لا يجوز تغيير الدولة أو العملة الأساسية أو النظام الضريبي بأثر رجعي بعد أول قيد مرحّل. يمكن للمستخدم تحديث الإعداد للمستقبل إذا كانت السياسة تسمح، لكن كل فاتورة وقيد يحتفظ بلقطة الدولة والنظام والرمز والمعدل وطريقة التقريب وقت الترحيل.

إذا أراد المستخدم تغيير الدولة بعد وجود بيانات، يعرض التطبيق تحذيراً ويقترح إنشاء ملف/سنة جديدة أو إجراء انتقال محاسبي مصرح، ولا يعيد حساب المستندات القديمة. أي Migration يضيف حقولاً أو جداول جديدة فقط ولا يعدل migrations v2 إلى v58.

## 4. معالج أول تشغيل

يظهر المعالج بعد Splash لأول تثبيت أو عند عدم اكتمال `onboarding_completed`. يجمع اللغة، الدولة، نوع النشاط، هوية المنشأة، العملة الأساسية، حالة التسجيل الضريبي، السنة المالية، الصندوق والمستودع الافتراضيين، ثم يعرض ملخص مراجعة قبل الحفظ.

يكون الاسم والدولة والعملة الأساسية والسنة المالية والصندوق الافتراضي إلزامية قبل أول ترحيل. يسمح التطبيق بتخطي الشعار والبيانات الاختيارية، لكنه لا يسمح بإنشاء قيد ناقص أو فاتورة ضريبية دون ملف ضريبي مكتمل.

بعد المعالج تعرض الشاشة «خطوتك الأولى» من 3 إجراءات حسب المجال. التجارة تبدأ بمنتج وشراء وبيع؛ الصيانة تبدأ بعميل وجهاز وأمر خدمة؛ المخبز يبدأ بوصفة ومواد خام وأمر إنتاج. جميع الوحدات الأخرى تبقى في «المزيد» والبحث.

## 5. العرض التدريجي

تحتفظ `MainScaffold` و`DashboardScreen` بكل المسارات، لكن مصدر الاختصارات يصبح `PresentationPreferences` بدلاً من قائمة ثابتة واحدة. يعرض التطبيق 6–8 إجراءات رئيسية للمجال، ثم يسمح للمستخدم بتخصيصها. الوظائف المتقدمة لا تختفي من النظام؛ تظهر في «كل الوظائف» مع بحث وتصنيف واضح.

يجب أن تكون أسماء العمليات مختلفة بوضوح: «فاتورة بيع»، «أمر خدمة»، «أمر إنتاج»، «تسوية جرد»، و«سند قبض/صرف». لا تستخدم الشاشة الواحدة مصطلحاً عاماً يخفي الأثر المحاسبي للعملية.

## 6. إصلاحات محاسبية قبل النشر العام

قبل اعتماد الإنتاج العام، تُنفذ بالترتيب التالي:

1. فصل الضريبة عن العملة واعتماد ملف Yemen بعد مراجعة محاسب محلي. يتضمن الملف المعدل العام والحالات الخاصة والإعفاءات وتاريخ السريان، ولا تُثبت الأرقام قانونياً من الكود وحده.
2. حفظ snapshot الضريبة في المستند والبند، واستخدام `InvoiceTotalsEngine` في الفواتير العادية ونقاط البيع والفواتير المتكررة.
3. منع الحذف الفيزيائي للسند المرحّل وتحويله إلى إلغاء منطقي مع سبب ومستخدم وتاريخ ومرجع القيد العكسي.
4. منع تغيير الدولة أو العملة الأساسية بعد أول ترحيل، أو توجيه المستخدم لمسار انتقال صريح.
5. إضافة إعادة تحقق PIN للنسخ والاستعادة والإلغاء وتغيير الإعدادات المحاسبية. يعلن الإصدار الأول نفسه single-owner/single-device ما لم تُبنَ أدوار حقيقية.
6. جعل أسعار الصرف البذرية غير صالحة للترحيل التلقائي حتى يعتمدها المستخدم أو يضيف سعر التاريخ المطلوب.

## 7. الاختبارات المطلوبة

تبدأ كل دفعة باختبار RED ثم التنفيذ ثم GREEN عبر CI:

| المجموعة | الاختبارات |
|---|---|
| التهيئة | إكمال المعالج، التخطي الآمن، الاستئناف بعد الإغلاق، منع الترحيل قبل الحد الأدنى |
| الدول | إضافة ملف دولة، تغيير معدل مستقبلي، ثبات snapshot للمستند القديم، رفض تغيير الدولة بعد الترحيل |
| الضريبة | معدل عام، معفى، صفري، معدل خاص، ضريبة شاملة/حصرية، تقريب بالوحدات الصغرى |
| العرض | preset لكل نشاط، تخصيص الاختصارات، بقاء كل المسارات متاحة، عدم تأثير العرض على القيود |
| السندات | مسودة قابلة للحذف، سند مرحّل غير قابل للحذف، إلغاء منطقي وقيد عكسي وسجل تدقيق |
| الصلاحيات | إعادة PIN للعمليات الحساسة، وضع single-device واضح، عدم حجب النسخ والتصدير عند انتهاء الترخيص |
| Android | جهاز فعلي، RTL، لوحة مفاتيح، الطباعة، الماسح، دورة النسخ والاستعادة، الترقية من إصدار سابق |

## 8. حدود الإصدار الأول

الإصدار الأول مناسب كتجربة تجريبية مضبوطة بعد اعتماد المحاسب المحلي، لكنه لا يُعلن جاهزاً للنشر العام قبل إصلاح البنود المحاسبية عالية الخطورة وتجربة Android الفعلية. لا يُضاف دعم دولة جديدة بمجرد إضافة عملة؛ يجب إضافة ملف دولة ونظام ضريبي واختبارات وحقول فاتورة ومتطلبات تقرير مستقلة.

## 9. معيار قبول التصميم

يُعتمد التصميم عندما يوافق المالك على نموذج «نواة موحدة + ملف دولة/ضريبة مستقل + مجالات تشغيلية + عرض تدريجي»، وعلى أن كل تغيير محاسبي يتم عبر Migration واختبارات TDD، وأن اختيار الدولة لا يعيد تفسير التاريخ، وأن جميع الميزات تبقى متاحة دون إغراق الشاشة الأولى.
